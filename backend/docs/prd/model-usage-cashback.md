## 1. 背景与事实边界

立项时系统已有独立返现余额 `users.cashback_quota`，用户可以将全部确认的返现余额转入普通 API 消费余额。银行卡、支付宝、微信和 USDT 提现目前不可用；返现与推广佣金分开。当时没有模型使用后自动产生返现的能力；本轮新增实现及部署记录见第 12 节，已部署但未启用生产返现。

转入普通余额后，现有余额字段不区分充值、赠送、返现等来源。因此本方案不承诺“只有现金充值消费才返现”或“返现转入后消费不能再返现”。本期采用余额按量消费统一参与的规则。

当前生产展示币种为 CNY，内部 quota 不能直接当作人民币。公共 `/pricing` 是报价表，旧模型详情抽屉刻意隐藏，本需求不恢复旧界面。

## 2. 目标与范围

目标：管理员能为指定模型设置可理解、可控制的使用奖励；用户完成有效消费后自动收到可核对的返现。

### 2.1 第一版纳入

- 在模型定价编辑器下增加返现开关、普通输入返现金额、输出返现金额。
- 单一返现模式：按实际结算的合格 Token 数折算，每百万 Token 为报价单位。
- 普通输入与输出独立配置；缓存读取和缓存写入不参与。
- 仅支持能够可靠区分普通文本输入、文本输出、缓存用量的文本 Token 按量消费。
- 第一版仅接纳已验证语义的非估算上游用量；本地估算、未知 usage、保守预扣和估算回退扣费不参与，即使该请求发生了扣费。
- 仅实际从普通余额结算扣费的消费参与。赠送余额、返现转入余额在此范围内；零扣费请求不参与。
- 全局返现占实际扣费的比例上限，以及规则版本快照。
- 自动入账、异常补发、返现明细、退款追回与核对能力。

### 2.2 第一版不纳入

- 按消费比例作为独立返现模式、按次/图片/视频/音频返现、阶梯、用户等级、渠道差异返现。
- 套餐权益消费、混合支付分摊、余额资金来源分账。
- 缓存专属返现、活动预算、用户日上限、活动有效期配置。
- 外部提现、新的返现有效期、历史消费追溯补贴、自动修改模型售价。

套餐优先但最终回退到余额的请求，以最终实际资金来源判断；套餐支付不因“套餐本身曾付费”而自动纳入。发现真正混合支付时暂不参与，并明确原因。

返现属于持续生效的模型优惠，没有活动预算扣完自动结束的隐含行为。

## 3. 管理员配置与用户体验

### 3.1 模型定价编辑器

在现有价格字段之后增加以下区域，不改变输入/输出售价的含义：

| 字段 | 类型和行为 |
| --- | --- |
| 使用返现 | 开关，旧模型和新模型默认关闭 |
| 普通输入返现 | 非负十进制金额，单位“元 / 百万 Token”；明确不含缓存读取、缓存写入 |
| 输出返现 | 非负十进制金额，单位“元 / 百万 Token” |
| 返现上限 | 只读展示全局上限“本次实际扣费的 X%”，链接到全局计费设置 |
| 计算示例 | 展示普通输入与输出指定用量下的返现，并说明受实际扣费上限限制 |

关闭时保留已保存金额，禁止产生新的返现承诺；开启时两项金额至少一项大于零。空值不等于零，不得保存不完整的开启配置。负数、非数值、无穷大和超出支持范围的金额必须拒绝。保存规则和版本需要原子生效，不能出现一半旧值一半新值。

不符合 Token 口径的模型不能开启返现，并解释适用范围。金额格式沿用现有十进制价格展示，不得出现浮点尾数。精度和最大输入值见第 11 节。

### 3.2 全局保护设置

- 增加全局发放开关，默认关闭；有效上限 X 未配置时不能开启。
- 增加统一上限比例 X，要求 `0 < X < 100%`；具体生产值由运营结合模型成本和折扣确定，本文不预设一个获批数值。
- 首发要求控制面、数据面的余额批量内存更新关闭，并在切换前排空旧队列。设置开启校验和数据面新请求准入均拒绝与 `BatchUpdateEnabled=true` 混用；已受理义务不因关停配置被取消。
- 全局开关和模型开关都开启，才允许新请求获得返现资格。
- Root 管理员关闭功能或调低上限，只影响之后接受的新请求；已经建立的返现义务仍按原快照结算或补发。
- 配置修改记录操作者、时间、旧值、新值及版本。第一版不新增单模型比例上限。

### 3.3 用户端

- 在现有 `/pricing` 报价表内，仅登录后的用户可见“使用返现”列；游客不渲染该列表头或单元格、不请求返现规则，退出登录后立即隐藏缓存内容。返现规则接口独立要求用户登录。登录后提供返现规则入口或展开说明，展示两项金额、缓存排除、余额按量消费范围及 X% 上限；不恢复旧模型详情抽屉。
- 对外说明采用“普通输入按 Y 元 / 百万 Token 计算，单次返现最高为实际扣费的 X%”，不能省略封顶条件宣传无条件固定返还。
- 完整规则必须说明“仅对符合范围、具备有效上游用量的余额消费返现；估算/未知用量不参与”。单项金额为零表示该类 Token 不返现。
- 全局或模型关闭后，报价表显示当前未开启返现，不继续展示为正在生效的优惠；进行中与历史请求仍显示自己的规则和到账结果。
- 消费记录展示本次返现，区分待入账、待核对、已到账、不参与，并单独展示部分/全部撤销及其中的取消待发、已到账追回明细。
- 明确不参与（如套餐、估算用量）与异常待核实（如上游用量冲突）分开显示；不能把“暂时无法计算”伪装成无返现资格，也不保证异常最终一定发放。
- 钱包返现区域提供明细入口，至少可看关联消费、模型、返现金额、状态和时间；规则版本与技术错误信息放管理员视图。
- 达到上限时显示封顶原因；小额结果不能因展示两位小数被误解为未返现。
- 延迟入账的金额不计入可转出余额，不用“已到账”表示处理中。
- 继续沿用现有全额转入普通余额的操作，准确说明仅支持站内消费余额。
- 开发时所有新增 UI 文案必须遵循项目 i18n 技能及 en/zh 规则；本文中文说明不是可直接硬编码的组件字符串。

状态语义：待入账表示已确认应发金额，暂未成功记入余额；待核对表示资金或用量事实有疑问，尚不能确定最终金额；不参与表示已确认不符合本期条件。明确的估算/未知用量不无限挂在待入账。金额已确认但余额容量不足仍属待入账，并给管理员可处理原因。返现撤销进度与入账状态分开记录，允许“部分取消待发后，剩余金额已到账”。

## 4. 计算口径

### 4.1 数据定义

| 符号 | 定义 |
| --- | --- |
| I | 最终结算的普通文本输入 Token，不含缓存读取和缓存写入 |
| O | 最终有效上游用量中的文本输出 Token，使用固定归一化口径；不得重复叠加已包含的细分 Token |
| Ri / Ro | 规则快照中的 CNY / 百万 Token 返现金额 |
| Q | 该消费最终实际从普通余额扣除的非负整数 quota，已体现用户分组和折扣 |
| x | 该请求快照中的上限比例，满足 `0 < x < 1` |
| K | 快照中每人民币元对应的 quota 换算系数，来自现有币种/汇率规则 |

预扣款、预扣后补扣/退差额均不能单独充当 Q。Q 是该笔消费完整的最终扣费，不是结算 delta，也不是用户当前账户余额。

### 4.2 公式及精度

```text
基础返现（人民币） = (I × Ri + O × Ro) / 1,000,000
基础返现（quota） = 基础返现（人民币） × K
返现上限（quota） = Q × x
原始应发 C0 = floor(min(基础返现（quota）, 返现上限（quota）))
```

- 在足够精度的十进制/定点计算中完成公式，最后按内部最小 quota 单位向下取整一次；不能先按人民币分取整。
- `M = 1,000,000`，不用累计满百万才返现。
- `Q = 0`、不符合范围或 C0 为零时不增加余额，记录可解释的原因。
- C0 是原消费的原始应发金额，持久化后不因是否已发放或之后退款改变；无退款时最终入账 C0，发生退款时按第 6 节调整。
- 低于 1 quota 的尾数本期不跨请求累计；界面说明低于最小入账单位。拆分请求不应通过四舍五入获得额外返现。
- 不凭空认定人民币与 quota 等价；保存 Ri/Ro、K、x、Q、I/O 和规则版本，以便复算，后续汇率变化不重算历史返现。
- 沿用项目 quota 安全转换及 Checked 审计机制，禁止裸浮点转整数。异常数量或换算不应静默变成巨额返现；超界进入待处理并保留原因。

### 4.3 Token 来源与模型身份

- 使用服务端取得的非估算上游最终用量，不能接受客户端提交的返现数量，也不能用 `max_tokens` 或请求长度直接发放。
- 复用已有上游语义解析，但建立含义固定的普通文本输入/输出口径。[表达式系统](../../pkg/billingexpr/expr.md)的 `p/c` 会随表达式引用缓存、图片、音频变量而改变，不能直接作为返现 I/O；增加或移除计费表达式变量不得改变同一实际用量的基础返现。
- 不同上游可能将缓存包含在输入总量中，也可能分别上报。实现时必须确认现有归一化字段，不得无条件再减一次缓存，也不得把缓存重复计入普通输入。
- OpenAI 原生缓存读/写前缀可能合法重叠，普通输入按 `max(0, 输入总量 - 缓存读取 - 缓存写入)` 计算，仍保留合格输出返现；单个缓存分类超过输入总量、负数等真正异常进入核对。
- 第一版整笔排除明确的图片/音频/视频/文件输入，以及请求指定媒体输出或 image_generation 工具的调用；不能因上游遗漏媒体细分字段而把媒体 Token 当普通文本返现。普通文本输出包含上游计费的推理 Token，已包含的数量不再加一次。
- 缺失、冲突或负值用量不能伪装为“正常零返现”；没有可靠口径的协议/模型不开放返现，运行中异常进入待处理。
- 第一版排除 `Estimated`、本地估算、usage unknown、保守保留预扣及估算回退记录。上游计量语义缺失时，不以客户端请求格式推断其已满足返现条件；协议明确保证缺省为零的字段须在支持清单中逐项验证，其他缺失缓存字段不能直接按零处理。
- 返现绑定用户侧模型定价标识，与用户看到的报价保持一致。渠道重试、上游模型映射不能改变同一请求已确定的返现规则。具体字段映射须在技术设计时验证，不允许直接猜测字段名。

## 5. 发放时机与规则生命周期

1. 接受请求并确定用户、模型和计费条件时，固定全局/模型开关、规则版本、Ri/Ro、x、K；在首次上游调用前完成。
2. 请求执行过程中不发放返现。中途重试复用同一业务请求的规则；不得按每个上游尝试重复返现。
3. 最终扣费已可靠持久化，且资金来源和用量符合条件，才产生应发返现；`SettleBilling` 返回 nil、缓存扣减成功或日志存在都不能单独证明这一步完成。
4. 可靠保存返现义务后入账。正常路径结算后自动到账；发生暂时性故障时显示待入账并自动重试，不要求用户再次调用模型。
5. 返现流水与返现余额变动一起提交。已到账资金才能转入普通余额。
6. 资金未成功结算时不先发放；后续资金结算恢复成功后，按原快照继续处理。返回错误但资金可能已经提交时，按下述部分成功规则判断。

资金扣费已持久化、但 API 令牌额度调整失败属于部分成功，不能仅因函数返回错误就永久取消返现或再次扣费。应从持久化资金事实判断资格，将令牌修复单独追踪；资金状态不明时先待核实。

HTTP 成功码不是发放依据：流式中断但结算有效则参与；HTTP 200 但没有有效消费不参与。仅发起请求、预扣或首个输出都不构成返现。

同一消费的重复处理只能产生一次原始返现。后续消费更正采用关联原记录的调整流水，不能覆盖原记录或当作新消费再次发放。

## 6. 退款与消费更正

### 6.1 预扣退回

尚未形成最终有效消费时返还预扣款，不属于消费后退款，不产生返现及返现追回。正常结算退回多余预扣也不算第 6.2 节的退款。

### 6.2 已结算消费退款

全额退款撤销原始应发返现；部分退款按累计退款金额占原扣费金额的比例撤销，不重新按当前价格或当前规则算返现。撤销分为取消尚未发放义务和追回已到账金额，二者不能混用。Q、C0、累计退款 F、撤销目标 T 全部使用同一整数 quota 单位，退款不使用当前汇率。

```text
原始应发 C0 = 原消费按原规则计算并持久化的应发返现
累计应撤销 T = floor(C0 × 累计退款 F / 原扣费 Q)
本次需撤销 = T - 此前已取消待发金额 - 此前已追回金额
全部退款时 T 必须等于 C0
```

对本次需撤销金额，优先取消该消费尚未发放的义务；超出待发部分才需要追回已到账返现。已到账追回优先从当前可用返现余额扣回；不足部分从本次原始退款中抵扣；仅净退款进入普通余额。同一事务记录原始退款、取消待发、返现余额追回、退款抵扣和实际到账金额，保持非负余额且重试不重复。

每个退款事件必须有持久化唯一标识。对原消费的累计退款、撤销目标、已入账/待入账状态在同一事务内锁定或条件更新，约束 `0 ≤ F ≤ Q`，按数据库最新值计算，不使用事务外旧快照。退款、入账与钱包转入必须使用一致的并发保护；冲突后重读，不得重复增加累计退款。本次退款不得超过处理前剩余可退金额 `Q - F_before`；处理后累计退款 `F_after` 不得超过原扣费 Q。

示例：原消费 10 元、返现 1 元，全额退款时：

- 返现仍有 1 元：扣回返现 1 元，普通余额收到退款 10 元。
- 返现已全部转走或花掉：从退款中抵扣 1 元，普通余额收到 9 元。
- 返现只剩 0.4 元：扣回 0.4 元返现，从退款中抵扣 0.6 元，普通余额收到 9.4 元。

用户明细展示上述拆分，不能只显示“退款 10 元”却只入账 9 元。其他消费产生的可用返现同属当前返现余额，是否被本次追回使用必须在账目中说明。

返现完全尚未入账时发生退款，取消 T 的待发义务，剩余应发为 `C0 - T`。此时退款不用追回尚未入账的钱；不得用剩余 Q 重新套用基础返现/封顶公式。全额退款后剩余应发为零，不得再补发。若先取消一部分待发、再入账、再退款，始终使用原始 C0，并减去此前已取消待发与已追回之和，不能把净入账额改成新的基数。

例如原扣费 10 元、应发 0.30 元，在到账前退 5 元，最终返现为 0.15 元，与先到账后部分退款的净权益相同。退款、补发与余额转入并发时，必须保证最终一致的净金额。

本期不新增通用退款产品入口，但所有纳入返现的现有结算后退款/调账路径必须接入上述约束。缺少可可靠接入的路径时，技术设计必须明确新增内部能力或限制支持范围，不能声称现有预扣 Refund 已覆盖。

人工更正用量、返现配置错误追溯调整，以及不伴随消费退款的奖励追回，不直接套用上述退款公式。需要持久化更正记录及明确处理方案；在方案完成前进入管理员待核对，并暂停该消费尚未发放义务，防止旧任务继续补发。形成可审计的更正决定后才能恢复、取消或调整。不能静默扣出负数、删除流水、借再次调用补偿；独立奖励追回也不能擅自扣普通余额。

## 7. 账务可靠性与可追溯性

- 为真实消费结算建立持久化唯一标识，原始返现以该标识去重；不能只依赖进程内标志或用户可重复提交的请求头。
- 已核实现有 `BillingSession` 的互斥锁和状态只在会话对象内；非严格钱包路径在启用 `BatchUpdate` 后可能只写内存队列。实现必须补足可证明的持久化资金结算与恢复能力，不能把当前对象内去重视为跨节点/重启幂等。
- 消费账务成功到返现义务持久化之间不能留下无法恢复的丢单窗口。技术设计需证明事务或持久化恢复机制能够覆盖进程退出。
- 消费日志用于展示关联，不默认它与余额扣费同库同事务；不能仅从一条日志推断扣款成功。
- 已核实消费日志可关闭、可写独立 `LOG_DB`，写入失败仅记录错误；文本消费在结算报错后也可能继续写日志。结算凭据和返现义务必须独立于这些日志开关与写入结果。
- Redis 缓存只在数据库提交后更新；缓存故障不能导致已提交返现被重复发放。
- 用户返现余额等于历史余额基础加已入账返现、减转入普通余额、减从返现余额执行的追回，并计入经审计调整；从退款抵扣的追回不能再次减返现余额。
- 最少保存：用户、业务消费标识、模型定价标识、规则快照、资金来源、归一化用量及来源、原扣费 Q、基础返现、上限、原始应发 C0、累计已入账、已取消待发、已追回、累计退款 F、入账状态、退款/追回关联、创建/到账时间。这些金额含义独立，不能只用一个返现金额覆盖。
- 返现流水与现有 `cashback_withdrawals` 职责分开，后者继续记录转入普通余额。
- 待处理记录保留可重试原因，管理员能查询未入账义务及补发/追回结果。普通用户只能查看自己的数据。
- 未结算的新消费与已生效的历史义务分开处理：关闭功能不删除历史流水，也不取消合法待发返现。
- SQLite、MySQL、PostgreSQL 都必须支持；跨库日志、分离部署和缓存模式下不得绕过一致性要求。

| A23 | 原扣费 10 元、应发 0.30 元，到账前退款 5 元 | 最终入账返现 0.15 元，与先入账后退款的净权益一致 |

| A26 | 同一上游实际用量，表达式加入/移除缓存、图片、音频变量 | 合格 I/O 和基础返现不变；实际扣费变化只可能影响封顶 |
| A27 | 最终有扣费但仅存在估算/未知用量或保守预扣 | 本期不返现，显示明确原因，不宣传为所有扣费都返现 |
| A28 | 原消费 10 元、C0=1 元；到账前退 2 元，再入账，再退剩余 8 元 | 先取消待发 0.2 元，入账 0.8 元，再追回 0.8 元；C0 始终为 1 元，最终权益为零 |
| A29 | 同一消费两笔部分退款并发、重复退款事件、超额退款 | 最新累计 F 只增加合法唯一退款金额，累计撤销无遗漏，超额退款拒绝 |
| A30 | 人工用量/金额更正进入待核对，同时有自动补发任务 | 该消费未发义务暂停；审计决定落库后才恢复或调整，普通余额不被独立奖励追回擅自扣减 |

## 12. 第一版实施记录（2026-09-03）

### 12.1 开工复核与交叉审查

用户要求产品、研发与研发组长确认能否满足原需求，符合即可开工。三个角色均确认满足“模型定价下按百万 Token 配置、实际使用并完成有效扣费后进入返现余额”，未确定的生产上限不阻碍默认关闭状态下的开发。

研发选择只为已启用优惠的钱包请求建立持久化会话，保留套餐及未参与请求原路径。钱包与 API Token 的预扣、追加预扣、结算及退回在主库同一事务完成，最终结算前先保存结算意图。没有可靠上游结果的历史预扣保留凭据，不按超时猜测发放或退款。

交叉审查修订：

- 异常用量/计算不能显示为确定无资格：计划标记待核对，资金结算仍可完成，奖励暂停。
- OpenAI 合法缓存前缀重叠不应清空输出返现：普通输入归零，输出按真实数量处理。
- 零预扣不应绕过零余额准入：新会话在事务内要求账户可用且余额大于零；既有义务的退款不受新准入限制。
- 最老失败任务不能阻塞全部待发奖励：恢复队列记录尝试时间并公平轮转。
- API 账本标识统一使用字符串 UUID；用户视图仅暴露自己可见的原规则与退款拆分。

| 模型定价下返现区域 | [model-cashback-settings.tsx](../../../frontend/src/features/usage-cashback/components/model-cashback-settings.tsx)，返现规则独立保存，冲突时重新加载 |
| 报价、钱包、消费详情 | [usage-cashback](../../../frontend/src/features/usage-cashback)，沿用现有报价表/钱包/消费记录，不恢复旧模型抽屉 |

金额 API 使用普通十进制字符串：CNY / 百万 Token 支持最多 8 位小数、范围 0～1,000,000；上限比例为最多 6 位小数且 `0 < x < 1`，UI 以百分比输入，最多 4 位小数。配置上限属于技术输入界限，不是推荐补贴金额。入账精度仍为整数 quota，用户明细保留足够小数及原始 quota 数方便核对。

控制面接口：

| 方法和路径 | 用途 |
| --- | --- |
| `GET /api/cashback/rules` | 当前返现规则及文本模型支持信息，必须登录；不随报价页公开设置放开 |
| `GET/PUT /api/cashback/settings` | 根管理员读取/按版本原子更新全局与模型配置 |
| `GET /api/user/cashback/records`、`GET /api/user/cashback/records/:id` | 当前用户分页记录及明细；支持 request_id 关联消费 |
| `GET /api/cashback/records`、`GET /api/cashback/records/:id` | 管理员核对记录、快照、流水与退款 |
| `POST /api/cashback/records/:id/retry`、`POST .../:id/pause` | 管理员重试持久化义务或暂停奖励核对 |
| `POST /api/cashback/records/:id/refund` | 根管理员按唯一退款事件执行消费退款及奖励撤销 |

本期提供受权限保护的内部退款/核对接口，不增加独立通用退款页面。无最终结算意图的 reserved 记录，以及独立奖励更正，仍须人工核对，不属于自动补发范围；不能直接更改原 C0 或拿当前费率重算。取消预扣时数据库不可用也可能留下这类待核对凭据。
