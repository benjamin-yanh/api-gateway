什么是余额击穿

本文所说的“击穿”是指请求开始时余额看似足够，但预扣或最终补扣之后，钱包 quota 或访问 Token 的 remain_quota 变成负数，或者上游消费已经发生但本地结算失败。

路径风险结果
实际消费大于预扣最终 delta > 0 直接补扣钱包或 Token 可变为负数
多个请求并发预扣先读余额、后扣减，缺少原子余额条件多个请求同时通过检查
信任额度旁路余额高于信任阈值时预扣为 0最终消费全部在结算阶段扣除
订阅额度不足订阅模型层拒绝超额结算通常不写成负数，但上游消费可能已发生

风险路径一：输出实际费用超过预扣

普通倍率计费的预扣位于 relay/helper/price.go:94-125：

preConsumedTokens = max(promptTokens, PreConsumedQuota)
+ maxTokens

preConsumedQuota = preConsumedTokens
× ModelRatio
× GroupRatio

最终结算位于 service/text_quota.go:355-367：

actualQuota = (
  promptQuota
  + completionTokens × CompletionRatio
) × ModelRatio × GroupRatio
+ cache/image/audio/tool/otherRatios

普通倍率预扣没有对 maxTokens 应用 CompletionRatio。未传 max_tokens 时，普通倍率路径也不会自动为输出使用 8192 回退值；8192 回退只存在于阶梯表达式计费。

示例

promptTokens = 1000
maxTokens = 500
CompletionRatio = 4
ModelRatio = 1
GroupRatio = 1

预扣 = 1000 + 500 = 1500
实际输出 300 Token 时：
实际费用 = 1000 + 300 × 4 = 2200
补扣 delta = 2200 - 1500 = 700

若预扣后只剩 100 额度，补扣 700 后余额可能成为 -600。

风险路径二：扣减不是原子余额检查

钱包扣减见 model/user.go:1257-1279：

UPDATE users
SET quota = quota - ?
WHERE id = ?

Token 扣减见 model/token.go:412-438：

UPDATE tokens
SET remain_quota = remain_quota - ?,
    used_quota = used_quota + ?
WHERE id = ?

两个更新都没有 quota >= amount 或 remain_quota >= amount 条件。预扣前余额读取与实际扣减也不是同一个原子操作。

并发示例

初始余额 = 1000
请求 A 读取 1000，准备预扣 800
请求 B 读取 1000，准备预扣 800
A 扣减成功
B 扣减成功
最终余额 = -600

结算如何补扣

service/billing_session.go:41-78 使用：

delta = actualQuota - preConsumedQuota
delta动作
> 0钱包/订阅和 Token 补扣
< 0退还差额
= 0不调整

钱包补扣调用 WalletFunding.Settle，随后 Token 补扣调用 DecreaseTokenQuota。若资金来源已结算但 Token 调整失败，代码记录系统错误并将会话标记为已结算，避免错误退款，但可能留下资金和 Token 统计不一致。

严格防止击穿需要什么

  1. 普通倍率预扣按 maxTokens × CompletionRatio 预留输出费用，并计入缓存、图片、音频、工具调用和其他可提前确定的费用。
  2. 未传 max_tokens 时使用协议/模型安全上限，或根据余额反算允许的最大输出 Token。
  3. 钱包扣减使用原子条件更新：WHERE id=? AND quota>=?，并检查 RowsAffected==1。
  4. Token 扣减使用原子条件更新：无限额度与有限额度分支明确隔离。
  5. 钱包、Token、订阅预留和退款应处于可恢复的一致性协议中；至少保证任何一步失败时都有幂等补偿记录。
  6. 并发测试覆盖：同一用户、同一 Token、多个请求同时预扣；最终余额不得小于 0。

只修改预扣公式不能解决并发击穿；只增加数据库条件也不能解决预扣不足后的上游经济损失。两部分必须同时处理。
