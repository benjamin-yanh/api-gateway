一、先看结论

从代码视角，网关可以压缩成一条“入口—策略—转发—结算”主链。

用户请求不是直接进入某个供应商 SDK，而是先进入统一协议入口；网关在真正发起上游 HTTP 请求前完成身份、模型、分组、渠道、限流、请求校验、Token 估算和预扣费。进程级中间件还会在路由前提供 Recovery、Request ID、版本、I18n、日志和 Session 上下文。
Client
  → 进程级中间件（Recovery / RequestID / Version / I18n / Logger / Session）
  → Gin 路由与通用中间件
  → TokenAuth / ModelRequestRateLimit / Distribute
  → GetAndValidateRequest + GenRelayInfo
  → Token 估算 + ModelPriceHelper + PreConsumeBilling
  → 渠道适配器 Convert + DoRequest
  → 上游 Provider
  → DoResponse / StreamScanner / Usage
  → SettleBilling + Log + (必要时) Retry / Refund
  → Client
入口

统一协议接入

/v1、/v1beta、/mj、/suno 等路由把 OpenAI、Claude、Gemini、Rerank、图片、音频、Realtime 和任务接口归一到 Relay。

策略

鉴权与渠道调度

Token 决定用户、分组、模型限制和可选的指定渠道；Distribute 决定是否命中渠道亲和缓存或执行优先级/权重选择。

执行

适配器转发

Adaptor 负责 URL、Header、请求体转换、上游调用和响应解析；同一个入口可映射到多个供应商协议。

账务

预扣—结算闭环

请求前按估算 Token/价格预扣，响应后按真实 Usage 补扣或退款，失败时回滚并记录渠道错误。

五、渠道亲和性、Token 指定渠道与自动切换

普通 Token：动态调度

普通 Token 不绑定单个渠道。网关按 TokenGroup + Model + RequestPath 取满足条件的 Ability，先按优先级，再在同优先级内按权重随机。

实现：service/channel_select.go:84、model/channel_cache.go:114。

管理员指定渠道

管理员可以使用 sk-<token-key>-<channel-id> 形式。Distribute 直接加载该 ID 并检查启用状态；普通用户指定渠道会被拒绝。

实现：middleware/auth.go:448、middleware/distributor.go:35。

渠道亲和性

规则先按模型、路径、User-Agent 过滤，再从 context/header/JSON 路径提取 Key；缓存映射为“规则 + 模型/分组 + Key → channel_id”。成功后写回 TTL 缓存，后续请求优先复用。

实现：service/channel_affinity.go:550、service/channel_affinity.go:713。

故障切换

错误进入 shouldRetry。HTTP 状态码、错误标记、剩余次数、指定渠道和亲和性规则共同决定是否切换；auto + cross_group_retry 只有在当前组优先级耗尽后才按用户自动组顺序继续尝试。

实现：controller/relay.go:325、service/channel_select.go:84。

同一个请求的渠道切换时序

retry = 0：选择最高优先级满足渠道 A
  → A 请求失败
  → shouldRetry(error) == true
retry = 1：选择下一优先级渠道 B；只有 auto 且 cross_group_retry 开启、当前组优先级耗尽时才换到下一个分组
  → B 成功
  → 以 B 的响应 Usage 结算
  → 若亲和性 switch_on_success，则把 Key → B 写回缓存
  → 日志记录 use_channel = [A, B]
注意：预扣通常发生在重试循环前；重试只改变下游渠道，不会重复向用户预扣整笔额度。普通状态码重试会被“指定渠道”和亲和规则的 skip_retry 阻断；渠道级错误有单独的错误分支。最终由真实 Usage 的结算路径补扣或退款。

六、网关如何到达下游并把响应带回来

1. 选择适配器

relay.GetAdaptor(apiType) 把渠道类型映射到 OpenAI、Claude、Gemini、Jina、Cohere、AWS、Vertex 等实现；同一 APIType 也可能复用 OpenAI 兼容适配器。

代码：relay/relay_adaptor.go:54。

2. 构建上游请求

Adaptor 初始化后实现 URL、Header 和请求体转换。Relay 会先做模型映射、系统提示处理、pass-through 判断，再执行参数/头覆盖。

代码：relay/compatible_handler.go:42、relay/channel/adapter.go:18。

3. 发送与解析

DoRequest 发 HTTP/WebSocket；非 2xx 响应进入统一错误处理；成功响应由 DoResponse 解析为 Usage 或流式/任务结果。

代码：relay/compatible_handler.go:188、relay/helper/stream_scanner.go:77。

4. 返回客户端

普通请求返回统一 JSON；Claude 返回 Claude 错误结构；Realtime 使用 WebSocket；SSE 由 StreamScanner 逐事件透传并维护结束原因。

代码：controller/relay.go:89、relay/helper/stream_scanner.go:77。

异步任务路径

图片、视频、音乐等任务使用 TaskAdaptor：先校验和估算账单，提交上游任务并保存任务 ID，之后由 FetchTask/ParseTaskResult 轮询；任务终态再执行实际额度调整。这条路径与同步 Chat 的差异是“请求返回时上游任务还没有完成”，因此需要在提交前锁定预扣。

七、名词解释

名词含义代码中的作用
Gateway / 网关对外统一接入、认证、调度和计费，对内调用多个 AI 上游的服务。由 Router、Middleware、Controller、Relay 和 Service 共同组成。
Relay把内部统一请求转发为下游供应商请求，并将下游响应转换回客户端格式的执行路径。controller/relay.go 与 relay/。
RelayFormat客户端请求采用的入口协议类别，例如 OpenAI、Claude、Gemini、Rerank、Realtime。决定 DTO 解析、处理器分支和返回错误格式。
Channel / 渠道一个上游服务配置，包含供应商类型、Base URL、Key、模型能力、分组、优先级和权重。model.Channel；由 Distribute 选择。
Ability / 能力渠道在某个分组下支持某个模型的关系记录。选择器用它过滤 group/model/enabled/priority/weight。
Adaptor / 适配器把统一 Relay 请求转换成某一上游协议的实现。实现 URL、Header、Body、DoRequest、DoResponse。
Token用户调用网关的访问凭证，不是模型输入 Token。决定用户、额度、分组、模型限制及可选的指定渠道。
模型 Token模型计费单位，通常由文本编码或媒体估算/上游 Usage 得到。用于预扣、真实结算、日志和限流统计。
TokenGroup / UserGroup渠道与价格策略的逻辑分组。控制可用渠道、倍率、自动分组和跨组重试。
Channel Affinity / 渠道亲和性按会话/业务 Key 在一段 TTL 内复用同一个渠道。缓存 Key → Channel ID，减少多轮请求漂移。
Priority / WeightPriority 决定故障切换层级；Weight 决定同层候选的随机比例。选择器先 priority 后 weight。
RelayInfo一次 Relay 请求的运行时上下文。贯穿用户、模型、渠道元数据、计费、重试、流状态和响应审计。
Pre-consume / 预扣上游调用前先锁定预计需要的额度。防止用户在请求执行期间额度被并发消耗。
Settle / 结算收到真实 Usage 后将预扣调整为实际消费。差额补扣或退款。
Pass-through保留客户端请求体或部分 Header，不做完整的标准格式转换。由全局/渠道设置控制，仍可能叠加覆盖操作。
StreamScanner流式响应扫描器。解析 SSE/事件、记录首字节/结束原因、处理客户端断开和上游异常。
RetryParam渠道重试状态。保存当前 retry 次数、分组、模型和请求路径。

  • 不要把预扣额度误写成最终消费额度。

交付前自检清单

  • 入口是否包含统一协议、模型列表、Realtime、任务接口的代表路径。
  • 鉴权是否解释了 Token 有效期/额度、IP、用户状态、分组和模型限制的实际边界。
  • 渠道选择是否同时覆盖指定渠道、亲和缓存、优先级、权重和自动跨组。
  • 计费是否区分 Token 预估、价格预扣、真实 Usage 结算和失败退款。
  • 请求体在 Distributor、校验和每次 retry 之后是否都能通过 BodyStorage 复位重读。
  • 下游是否说明 Adaptor 的 URL/Header/Body/Response 四个边界，以及多 Key 轮换。
  • 响应是否覆盖普通 JSON、SSE、WebSocket、错误和异步轮询。
  • 是否说明亲和缓存失效、skip_retry、指定渠道、status mapping 和 auto-ban 的边界。
  • 是否覆盖 Redis/内存缓存、数据库兼容和限流降级路径。
  • 图和文字是否能够互相验证，关键结论是否有源码路径和行号。
